10. 정정 1 — 학습 경로 통합 (2026-11-17, TRNK 검토 ① 반영)
- 정정: 7절의 "LAG 경로 규칙 미검증"은 정확하지 않았다.
  - 품목 연결은 형식이 우연히 같아서 이미 이어져 있었다.
  - 자료 종류는 조건 형식({form_key} vs {supplier, marker})이 달라 끊겨 있었다.
- 통합 내용
  - 조건 정의를 learn.facts_for 하나로 모았다. 사례 키, LAG 판정 초안, 직접 지시 규칙, 규칙 적용이 모두 이 함수를 쓴다.
    - doc_kind = {상대 업체, 원문 표지}
    - item_map = {상대 업체, 품목 원문}
  - 규칙 적용 절차도 learn.decide 하나로 모았다. 문답 경로와 기존 접수 경로가 같이 쓴다.
    - 서버가 직접 활성 규칙을 찾는다. 모델이 규칙을 인용했는지는 보지 않는다.
    - 유효기간과 충돌 보류는 기존과 같다.
    - 원문 표지와 다른 방향의 종류 규칙은 제외한다. 단, 보관만(other)은 장부를 바꾸지 않으므로 제외하지 않는다.
  - 직접 지시는 'LAG를 검증 없이 바로 판정'하는 지름길이다. 결과로 생기는 규칙 버전의 형식은 판정 경로와 같다.

- 남은 것(검토 ②~④): 근거별 확정 범위(칸별 확정), 소유자 칸, 반납 보관만을 '장부 반영 미결'로 표시, API 호출 중 전체 잠금 해제, 시험 절차 안내 정정.

11. 정정 2 — 근거별 확정 범위 (2026-11-17, TRNK 검토 ② 반영)
- 원칙: 자료 한 건의 판단을 칸으로 나누고, 근거는 자기가 확정할 수 있는 칸만 채운다. 빈 칸만 묻는다.
- 칸: 종류, 상대 업체, 줄별 수량·품목·소유자(임대품만).
- 근거와 확정 범위(dialog.SLOT_EVIDENCE)
| 근거 | 확정하는 칸 |
| 원문 종류 표기(document) | 종류 — 문서가 주장하는 이동 |
| 원문에 적힌 업체명(document_name) | 상대 업체 |
| 원문에 적힌 숫자(document_value) | 그 줄의 수량 |
| 기준정보 정확 일치(master_exact) | 품목만(수량·방향·소유자 아님) |
| 보낸 업체 = 등록 소유자(sender_is_owner) | 소유자 |
| 이번 사용자 답(user_answer) | 그 질문의 칸, 이 사건에 한함 |
| 승인된 규칙(rbk) | 조건 범위 안에서 그 규칙의 칸(doc_kind / item_map / owner_map) |
- 바뀐 동작
  - 모델이 읽은 수량은 원문에 같은 숫자가 있을 때만 확정한다. 없으면 "97개가 맞나요?"로 확인한다(fixture 시험에서 실제로 잡혔다).
  - 모델이 읽은 상대 업체는 원문에 그 이름이 있을 때만 확정한다. 없으면 확인한다.
  - 기준정보 정확 일치는 서버가 직접 확인한다(모델의 item_ref를 믿지 않는다).
  - 임대품 소유자 칸 신설. 보낸 업체가 등록 소유자가 아니면 묻는다.
    - 답은 사례(owner_map)로 남고, LAG → 판정 → 규칙으로 학습된다(시험 통과).
    - 장부: value_move.owner에 반영한다. 공장 임대품 요약도 소유자별로 나눈다.
    - 처음 보는 소유 업체는 사용자 답을 근거로 거래 상대에 추가하고 기록을 남긴다.
  - 확정 근거는 처리안 검증 기록(dialog_proposal.validation.confirmations)에 칸별로 저장한다. 화면의 '무엇으로 확정했나'에서 볼 수 있다.
- 실제 API 증거
  - J01: 질문 2개(품목, 소유자). 근거는 상대 업체=원문 업체명, 종류=원문 표기, 수량=원문 숫자, 품목·소유자=이번 답변. 장부: KPP 팔레트 97, 소유자 LOGISALL.
  - "KPP 입고전표 / KPP 팔레트 30": 질문 0개. 품목=기준정보 일치, 소유자=보낸 업체가 등록 소유자. 장부: 소유자 KPP.
  - 공장 임대품 요약: KPP 소유 230 / LOGISALL 소유 97.
- 시험: 85개 통과.
- 사용자 확인 필요: P10이 'LOGISALL 소유 팔레트'라면 기준정보에 별도 품목(LOGISALL 팔레트)으로 둘지, 'KPP 팔레트를 LOGISALL이 전달'한 것인지. 지금 구조는 둘 다 표현할 수 있다(품목 / 소유자 칸 분리).
- 기존 JSON 접수 경로에는 소유자 칸 확인이 아직 없다(등록 소유자 그대로).
