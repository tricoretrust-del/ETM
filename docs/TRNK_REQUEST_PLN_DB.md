# [재요청] 운영 PLN을 DB 구조에 포함하도록 지시서 정정 요청

- 수신: ETM TRNK (DEV 지시서 작성 담당)
- 발신: CLD (Claude 개발 담당), 사용자 확인 후 전달
- 작성일: 2026-11-17
- 대상 문서: ETM Docs `[ETM]_Nov.17,2026` — RBK v0.3(+v0.4 검토안), PLN v0.1, LAG v0.1, DEV-001(용어 정정 주석 포함), DEV-002 v0.1
- 요청 종류: 지시서 정정 및 DEV-003(또는 DEV-002 개정) 작성 요청

---

## 1. 요약

**사용자 결정:** "PLN도 DB 구조의 하나가 되어야 한다."

**현재 지시서:** CUR을 PLN과 LAG로 나누면서 운영 DB에는 **운영 RBK·운영 LAG만** 남겼습니다. PLN은 "개발 관리 문서로 유지, 별도 운영 DB 불필요"로 정했습니다(DEV-002 §1).

**원인으로 보이는 지점:** 처음 설계(CUR v0.3)의 운영 DB에는 **운영 커리큘럼**이 있었고, 그 역할은 검증·**개선·확장 과제**와 **완료 조건·진행 상태**였습니다. 명칭을 정정할 때 이 중 '검증' 부분만 운영 LAG로 옮겨졌습니다. '개선·확장 과제와 진행', 즉 계획 부분은 문서 PLN으로만 옮겨져 운영 DB에서 빠졌습니다.

**결과:**
- 운영 중 드러난 사용자 필요(개선·확장 과제)를 프로그램 안에 기록하고 추적할 곳이 없습니다.
- LAG v0.1이 요구하는 "LAG → PLN 연결"을 구현할 수 없습니다.
- 사용자의 목표인 "완성된 룰북과 계획으로 사용자 필요를 역엔지니어링"이 막혀 있습니다.

**요청:** 운영 PLN을 운영 DB의 한 축으로 정의하는 지시서를 다시 작성해 주십시오(§5).

정리하면, 운영 커리큘럼이 맡던 '개선·확장 과제와 진행' 역할은 다음 세 곳 사이에 놓여 있습니다.
- 운영 LAG(DEV-001 정정본)
- 문서 PLN(LAG v0.1, DEV-002)
- 어디에도 없음(운영 DB 구성)

### 2.4 사용자 의도 (이 개발 세션의 사용자 발언)

> "룰북과 커리큘럼의 작성을 통해 점점 물어보는 것이 적어져야 하고 … 그 완성형 룰북과 커리큘럼을 통해 실제 사용자들이 겪고 필요로 하는 것이 무엇인지 역엔지니어링 할 수 있다."

> "PLN도 DB 구조의 하나가 되어야 한다."

여기서 말하는 역엔지니어링 재료는 두 가지입니다.
- 운영 중 쌓인 **확정 규칙**(RBK)
- 운영 중 드러난 **필요·개선·확장 과제와 그 진행**(PLN)

LAG만으로는 '무엇을 아직 모르는가'는 남지만, '무엇이 필요하고 어디까지 해결됐는가'는 남지 않습니다.

## 3. 판단

1. 처음 설계에서 운영 DB의 학습 축은 **룰북 + 커리큘럼(검증 + 개선·확장·진행)** 두 개였습니다.
2. 명칭 정정(CUR → PLN + LAG)은 문서를 나누는 작업이었는데, 그 분리가 운영 DB에도 그대로 적용됐습니다. 그 결과 운영 커리큘럼 중 '계획' 부분이 **문서 전용 PLN**으로 옮겨지면서 운영 DB에서 사라졌습니다.
3. 이 변화는 TRNK의 '채택 대기' 명칭 정정안에서 시작됐습니다. 그런데 DEV-002 §1에서 "PLN은 문서, 운영 DB 불필요"로 **구현 범위가 확정**됐습니다. 사용자가 PLN을 운영 DB에서 빼기로 결정한 기록은 Docs 안에서 찾지 못했습니다.
4. 따라서 이것은 **용어 정정 과정에서 생긴 범위 축소 오류**로 판단합니다. 사용자 결정과 처음 설계에 따라 운영 PLN이 운영 DB의 한 축이 되어야 합니다.

## 4. 현재 구현에 미친 영향 (CLD 자체 점검 포함)

| 항목 | 상태 |

| 운영 DB | `rule`/`rule_version`(RBK), `lag`/`verification`/`judgment`(LAG)만 있음. PLN 테이블 없음 |
| 이전 커리큘럼 이관 | DEV-002 §1에 따라 계획 성격 2건("처리 건수 집계 규칙", "스캔 출력 어댑터 연결")을 `moved_to='PLN'`으로 **표시만** 했음. 옮겨 갈 실제 대상이 없어 사실상 보관만 된 상태 |
| CLD 실수 | 설계 질문 2건("미결·완결 세부 상태 검증", "승격 기준")을 **운영 LAG**에 넣었음. 이 둘은 TRNK 설계 LAG 또는 PLN 항목에 가까움. 운영 사례가 붙을 수 없어 계속 '접수' 상태로 남음 |

## 5. 재요청 사항 — 결정과 지시서 작성을 요청합니다

### 5.1 결정 요청

1. **운영 PLN의 정의**: 운영 중 드러난 사용자 필요·개선·확장 과제와 그 진행·완료를 기록하는 운영 DB 축으로 정의할지. TRNK 문서 PLN(설계·개발 순서)과는 계층이 다른 기록으로 둘지.
2. **세 축의 경계**:
   - 운영 RBK: 승인된 실행 규칙
   - 운영 LAG: 모르는 것, 검증할 질문·가설
   - 운영 PLN: 해야 할 것, 필요·개선·확장 과제와 진행·완료 조건
   - DEV-001 §7의 "운영 LAG가 확장 과제·진행 상태를 보관"이라는 문장은 PLN 쪽으로 정정할지.
3. **연결 방향**:
   - LAG 판정 결과가 "개발·개선 필요"이면 PLN 항목으로 연결할지
   - PLN 항목이 완료되면 관련 LAG 재검증이나 RBK 개정으로 이어질지
   - PLN에서 DEV 지시서로 넘어가는 경계를 어디에 둘지
4. **PLN 항목의 최소 필드와 상태**: 아래 초안을 검토해 주십시오.
5. **생성 주체·권한**: 운영 PLN 항목을 사용자만 만들지, 시스템 후보 제시를 허용할지(LAG처럼 자동 생성 금지를 적용할지). 우선순위와 완료 판정은 누가 하는지.
6. **TRNK PLN 문서와의 동기화**: 운영 PLN 항목 중 개발이 필요한 것을 TRNK PLN으로 올리는 절차. 반대로 TRNK PLN의 결정을 운영 PLN에 반영하는 절차.
7. **이관 정정**: 이전 커리큘럼 4건과 CLD가 운영 LAG에 넣은 설계 질문 2건의 최종 위치.

### 5.2 운영 PLN 최소 필드 초안 (CLD 제안 — 확정 아님)

| 필드 | 설명 |
|---|---|
| PLN ID | 고정 ID |
| 회사·범위 | 회사, 사건 종류, 필요하면 거래처·현장·품목 (RBK·LAG와 같은 범위 체계) |
| 필요·과제 | 사용자가 겪는 불편이나 필요를 한 문장으로 |
| 근거 | 연결된 사건·확인 기록·LAG·적용 기록 (외래키, 복수) |
| 기대 효과 | 예: "하루 질문 n건 감소", R01·R05 기준 |
| 완료 조건 | 관찰 가능한 기준 |
| 상태 | 예: 접수 → 계획 → 진행 → 완료 / 보류·기각 (상태 목록은 TRNK 결정) |
| 우선순위 | 결정 주체와 함께 기록 |
| 연결 | 관련 LAG·RBK 규칙 버전·DEV 지시서 참조 |
| 이력 | 상태 변경·판정 기록(누가, 언제, 왜) |

### 5.3 요청 산출물

- RBK·PLN·LAG 문서의 해당 문장 정정본(§2.2~2.3에서 지적한 곳)

  - 상태 전이와 권한

- 여전히 PLN을 문서 전용으로 유지해야 한다고 판단한다면, 그 근거와 사용자의 역엔지니어링 목표를 어디서 충족하는지에 대한 설명
