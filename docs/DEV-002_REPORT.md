## 2. 논리 관계도

```
 company ─┬─ event(사건, revision) ── intake(증빙·원문·해시)
          │      │
          │      ├─ confirmed_case(사실 확인·수정: 이전값·확정값·확인자·이유·원본 참조)
          │      ├─ decision_case(판단 확인: 상황 키·답·확인자 / 규칙이 처리했으면 rule_version_id)
          │      └─ rule_application(사건·리비전·규칙 버전·매칭 근거·입력 스냅샷·결과·이유)
          │                                 │
          ├─ lag ─┬─ lag_link(사건·확인 기록, 복수)          │
          │       ├─ lag_log(상태 이력: 보류·재개·기각)        │
          │       ├─ verification ─ verification_case(사례) │
          │       └─ judgment(LAG 판정)                     │
          │                                                 │
          └─ rule(고정 ID, 회사/공통, 사건 종류, 판단 종류)      │
                 └─ rule_version(변경 불가: 조건·동작·범위·유효기간·근거·LAG) ┘
                        └─ judgment(승인·중지·폐기: 정확한 버전·판정자·권한)
 app_user(역할) — 모든 판정·검증·LAG 등록의 주체
 command_log — 학습 명령 멱등성
```

모든 연결은 외래키입니다(`PRAGMA foreign_keys=ON`). `lag_link`는 최소 하나의 대상을, `judgment`는 LAG 또는 버전 중 정확히 하나를 가리키도록 CHECK 제약이 있습니다.

## 3. 상태 전이

**LAG**: `open(접수)` → (검증 기록 추가) → `awaiting(판정 대기)` → 판정 → `closed(종료)`
- 판정 결과 `outcome`: `rule`(규칙 반영) / `narrowed`(범위 축소 반영) / `rejected`(기각)
- `held(보류)`: 종료 전 어느 상태에서나. 이유 저장
- `reopen`: closed·held → open. 이력(`lag_log`)과 판정(`judgment`)에 남음
- 판정은 검증 기록이 있는 `awaiting`에서만 가능

**규칙 버전**: `pending(승인 대기)` → 승인 → `active` → `suspended`(중지, 재개 가능) / `superseded`(새 버전 승인 시) / `retired`(폐기)
- 수정은 새 버전(`create_version`). 기존 버전 내용은 DB 트리거가 거부
- 승인은 정확한 version_id 대상. `pending`이 아니거나 **더 새로운 버전이 있으면 거부**(오래된 승인 방지)
- 새 버전 활성화와 이전 활성 버전 대체, 승인 판정 기록은 한 트랜잭션. 규칙당 활성 버전은 최대 1개(부분 유일 인덱스)
- LAG 판정, 규칙 활성화, 개발 완료는 서로 독립. 규칙이 필요 없는 LAG 는 기각 등으로 종료

## 4. 권한

| 역할 | 할 수 있는 일 |
|---|---|
| operator (직원) | 사실 확인, LAG 등록, 검증 기록, LAG 판정(보류·기각·규칙 반영 = 승인 대기 버전 생성) |
| approver (대표) | 위 + 자기 회사 규칙 버전 승인·중지·폐기 |
| admin | 공통 규칙(company_id NULL) 승인 — 현재 계정 없음 |
| system | 이관·초기 제안 기록만. 판정·승인 불가 |

화면 상단 오른쪽 '사용자' 선택으로 확인자가 바뀌고, 요청 헤더 `X-ETM-User`로 서버에 전달됩니다. **실제 로그인·인증은 아직 없습니다**(§7 미결).

## 5. 범위 매칭·충돌

- 조회: `status='active'` + 회사 일치(또는 공통) + 사건 종류 + 조건(사실 일치) + 범위(거래처·현장·품목 일치) + 유효기간(거래일 기준).
- 실행 동작은 허용 목록만: `compare_pallets`, `set_doc_kind`, `map_item`. 형식 검증 후 저장·실행. 자연어 설명은 실행하지 않음.
- 서로 다른 동작의 활성 버전이 겹치면 **그 처리만 보류**하고 확인 카드에 "활성 규칙 충돌(…) — 우선순위 정책이 없어 보류"를 표시, 적용 기록 `held_conflict`. 나머지(제품 재고 등)는 진행.
- 규칙 승인은 재고·돈을 직접 바꾸지 않습니다. 과거 사건은 재계산하지 않습니다.

## 7. 미구현·미결정 (TRNK 판단 필요)

1. **인증**: 사용자 선택은 화면 드롭다운과 헤더뿐입니다. 실제 로그인·위조 방지는 없습니다. 단일 PC 사용을 전제로 합니다.
2. **후보 제시 기준 3건**은 잠정값입니다(LAG-001 '승격 최소 근거'와 연결).
3. **충돌 우선순위 정책**이 없습니다. 현재는 항상 보류합니다.
4. **공통 규칙 승인(admin)** 경로는 구현했지만 계정이 없습니다(LAG-002 범용화 경계).
5. **기본 동작**(손글씨·불확실 확인, 기준정보 정확 일치 연결, 과거값 덮어쓰기 금지, 경고 후 확인, KPP 임대료 미생성)은 코드에 고정되어 있습니다. 이것들을 운영 규칙으로 올릴지는 결정이 필요합니다.
6. **범위 축소(narrowed)** 판정은 범위를 인자로 받지만, 화면에는 범위 입력 칸이 아직 없습니다(API·테스트로만 가능).
7. **사건 재처리 절차**(규칙 변경 뒤 과거 사건을 명시적으로 다시 계산하는 기능)는 만들지 않았습니다. 과거 사건은 자동으로 재계산하지 않습니다.
8. **KPP 비용 발생 조건**은 검증된 계약 정보가 없어 계산하지 않습니다. LAG 로 남길 대상입니다.
9. 기존 DB 이관: 이전 방식으로 승인된 학습 규칙(L-xxx)은 권한·버전 기록이 없어 `retired`로 두고 재승인이 필요하다고 표시했습니다. 시험 DB 는 `--reset` 을 권장합니다.
