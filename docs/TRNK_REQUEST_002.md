## 2. 이미 처리한 결함 (보고)

**[결함 1] PLN 실행 결과가 LAG 검증 근거가 되지 못함 → 수정 완료**

| 항목 | 내용 |
|---|---|
| 증상 | LAG 검증 기록이 판단 기록(decision_case)만 근거로 받았다. 사건에서 시작한 LAG는 PLN을 완료해도 검증 → 판정으로 갈 수 없어 '접수' 상태에 영구히 머물렀다 |
| 위반 | DEV-003 §4 "검증 기록은 LAG에, 실행 기록은 PLN에 책임을 두고 같은 증빙을 참조한다. 결과 문장을 양쪽에 다시 입력시키지 않는다" |
| 수정 | 마이그레이션 0005 `verification_evidence`. 검증 근거로 **완료된 PLN, 사건, 증빙**을 받는다. 관찰 결과를 비우면 PLN 실행 결과를 그대로 참조한다. 완료 전 PLN 사용 금지, 회사 경계 검사(DB 트리거) |
| 검증 | 테스트 3개 추가(전체 50개 통과, Python 3.10·3.11·3.13). 브라우저에서 사건 → LAG → PLN 완료 → PLN 결과로 검증 → 판정 대기 → 기각까지 확인. PLN 완료가 LAG를 바꾸지 않고, LAG 판정이 PLN을 바꾸지 않는 독립성도 유지 |

## 4. 결정 요청 항목

### 항목 2. LAG 판정을 실행 규칙으로 바꿀 수 있는 판단 종류가 3개뿐

| | |
|---|---|
| 현상 | "규칙 반영" 판정은 자료 종류(doc_kind), 입고 품목(item_map), 팔레트 대조(pallet_check)에만 가능하다. 사건에서 나온 일반 질문(예: "팔레트 부분 회수 처리")은 판정해도 실행 규칙이 될 수 없고 기각·보류만 가능하다. 화면에는 '규칙 반영' 버튼이 보이지만 누르면 거부된다 |
| 원인 | DEV-002 §3 "실행 가능한 동작은 코드에 정의된 허용 목록만"에 따라 동작 3종만 구현됨 |
| 결정 요청 | (a) 다음에 허용 목록에 추가할 판단·동작 종류와 우선순위 (예: 거래처·품목 연결, 담당자 후보 선택, 중복 여부, 팔레트 부분 회수) (b) 실행 동작이 없는 LAG를 "규칙 반영"으로 판정하면 → '참고 규칙(자연어, 실행 안 함)'으로 남길지, 개발 요청(TRNK PLN·DEV)으로 연결할지 (c) 화면에서 실행 불가능한 판정 버튼을 숨길지 |

### 항목 3. 학습 재료가 응답의 10%뿐

| | |
|---|---|
| 현상 | 출하의 거래처·현장·품목 연결, 담당자 변경, 단위, 재고 부족, 중복 여부 응답은 사실 기록(confirmed_case)으로만 남고 판단 기록으로 남지 않아 후보가 될 수 없다. 손글씨 확인(하루 6건)은 RBK v0.3 "항상 확인"에 따른 의도된 고정 질문이다 |
| 결정 요청 | (a) 판단 기록으로 남길 응답 종류 (b) 손글씨 확인을 계속 항상 물을지, 규칙화 대상으로 둘지(예: 같은 기사·차량 반복이면 원본만 보여 주고 확인 생략) (c) 같은 날 같은 거래처·품목·수량 출하의 중복 확인을 학습 대상으로 할지 |
| 근거 | 시뮬레이션에서 규칙 승인 뒤에도 하루 8건이 남음(§3) |

### 항목 4. LAG·PLN이 일상 화면에 보이지 않음

| | |
|---|---|
| 현상 | 열린 LAG, 진행 중인 PLN, 기한은 오른쪽 이력이나 '남은 일'에 나타나지 않고 RBK·PLN·LAG 패널을 열어야만 보인다. 사건 화면에서 만든 계획과 같은 사건의 LAG는 자동으로 서로 연결되지 않는다 |
| 위험 | 기록이 쌓이지 않고 잊힌다(R10은 '필요한 것만 표시'이고, 이 항목은 그 '필요한 것'의 경계 문제) |
| 결정 요청 | (a) '남은 일'에 열린 LAG·PLN(담당 본인 것, 기한 임박 것 등)을 표시할 기준 (b) 사건에서 PLN을 만들 때 그 사건의 열린 LAG를 연결 후보로 제시할지 (c) 오른쪽 이력에 학습 동작(검증·판정·승인·계획 완료)을 한 줄로 남길지 |

### 항목 5. 역엔지니어링 재료로서 '왜'가 남지 않음

| | |
|---|---|
| 현상 | 규칙 설명이 "항목 구성이 [기사연락처·납품처·…]인 자료 → 입고"처럼 기계적이다. 판정 이유, 계획 목적, 사용자 불편 서술은 입력하지 않아도 된다 |
| 결정 요청 | (a) 판정·승인·계획 생성 때 짧은 이유(한 줄)를 필수로 받을지 (R01 입력 수고와의 균형) (b) 규칙·계획에 '사용자 필요' 서술 칸을 둘지 (c) 완성된 RBK·PLN·LAG에서 사용자 필요를 뽑아 보는 출력물(보고서)을 정의할지 |

### 항목 6. 같은 상황 판별(양식 키)이 민감함

| | |
|---|---|
| 현상 | 자료 종류 판단의 상황 키가 '항목 이름 목록 전체'다. "기사연락처"와 "기사 전화" 차이나 "비고" 줄 하나 추가만으로 다른 양식이 되어 처음부터 다시 배운다(직접 시험으로 확인) |
| 결정 요청 | (a) 상황 키 정의 방식: 핵심 항목만 / 보낸 업체 기준 / "이 양식과 같은가?"를 한 번 묻고 그 답을 학습 (b) 상황 키를 넓혔을 때 오적용 위험을 어디까지 허용할지(LAG-002 범용화 경계와 연결) |

### 항목 7. 수고 감소를 측정할 수 없음

| | |
|---|---|
| 현상 | LAG-004("학습된 규칙이 사용자 수고를 실제로 줄였는가")를 판단할 측정값이 질문 수와 자동 처리 수뿐이다. 처리 시간, 재입력, 수정 횟수는 기록하지 않는다 |
| 결정 요청 | (a) 측정 지표: 건당 질문 수 / 건당 처리 시간(접수 → 마지막 확인) / 사후 수정 횟수 / 규칙 적용 후 번복 횟수 등 (b) 기준선과 목표(PLN '하루 약 20건·1시간 이내' 가설과의 연결) (c) 측정 결과를 LAG-004 검증 근거로 자동 연결할지 |
