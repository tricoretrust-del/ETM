# DEV-001 설계 메모 (구현 제안 — 영구 구조 아님)

적용: RBK v0.3 · CUR v0.3 · DEV-001 v0.1 (2026-11-17)

## 1. 스택 선택

| 선택 | 이유 |
|---|---|
| Python 3.10+ 표준 라이브러리만 사용 | 설치할 의존성 없음, 무료, 복사해서 바로 실행 |
| SQLite 한 파일 | 무료·무설치, 트랜잭션 보장, 백업은 파일 복사 |
| 화면은 HTML 한 장 + 순수 JS | 빌드 도구 없음 |

가정: 한 사업장에서 1~수 명이 사용. 여러 사용자가 동시에 쓰거나 원격 접속하면 DB·배포 방식을 다시 정합니다(CUR §4 '구현 기술' 미확정).

## 2. 처리 흐름

```
입력(스캔·직접) → contract.normalize → intake()
   ├ 같은 내용 재수신 ─────────────→ 증빙만 연결, 추가 반영 없음
   ├ 같은 전표번호·다른 내용 ─────→ "같은 출하인가?" (예 → 차이만 기존 사건에 반영)
   ├ 다른 번호·같은 거래처/날짜/품목·수량 → "같은 출하인가?"
   └ 새 사건
        ↓
  sync_checks(): 물어야 할 것만 계산 (이미 답한 질문은 다시 묻지 않음)
        ↓
  reconcile(): 확정된 값으로 '목표 장부 상태' 계산 → 기록된 것과 차이만 기록
        ↓
  history 한 줄 (처리 1회 = 1줄, 사건 효과 묶음)
```

`answer()`(확인 응답)과 `revise()`(상세 화면 수정)도 같은 순서로 sync_checks → reconcile 을 거칩니다.
각 호출은 하나의 트랜잭션입니다.

### 이중 반영을 막는 방법 (DEV-001 §6)
- 반영은 '목표 − 기존 합계' 차이만 기록합니다. 같은 처리를 여러 번 해도 결과가 같습니다(멱등).
- 수정은 **반대 부호 조정 행**을 추가합니다. 이전 행을 지우지 않으므로 이력이 남습니다.
  예: 600 → 550 수정 시 `value_move`에 `+600(apply)`, `−50(revise)` 두 행이 남습니다.
- 금액은 `money_claim`(현재값)과 `money_log`(변경 이력)로 관리합니다.

### 부분 확정 (RBK v0.3)
- 열린 확인 요청이 걸린 필드에 의존하는 효과만 보류합니다.
  - 품목 줄은 줄 단위로 따로 반영합니다.
  - 팔레트 수량이 미확정이면 팔레트 이동만 보류하고 제품 출하는 반영합니다.
  - 받을 돈은 보류 줄이 있거나 단가가 없으면 **금액 NULL(미확정)**로 둡니다.
- 동일 여부 확인(identity)이 열려 있으면 그 사건은 아무것도 반영하지 않습니다.

## 3. DB 구조 (`etm/db.py`, 마이그레이션 0001)

| 논리 구성 | 테이블 |
|---|---|
| 기준정보 | `party`(거래처·공급·임대), `site`, `item`(product / rental), `price` |
| 사건 | `event`(확정 필드 JSON, 거래일·처리일 분리), `intake`(받은 원본 전부) |
| 가치 이동 | `value_move` (부호 있는 조정량, from→to, 소유자 `own` / `party:<id>`) |
| 채권·채무 | `money_claim`(amount NULL = 미확정), `money_log` |
| 남은 처리 | `obligation` (사건 × 종류: 출하 재고 반영, 팔레트 확인, 금액 확정, 수금, 운반 내역 확인, 운반비 지급, 팔레트 회수, 확인 대기) |
| 증빙·응답·수정·반영 이력 | `intake`, `check_item`, `confirmed_case`, `history` |
| 운영 룰북 | `rulebook` — 고정 규칙 6개(HW-CONFIRM, PALLET-DOUBLE, NO-OVERWRITE, UNCERTAIN-FIELD, KPP-NO-AUTO, STOCK-WARN) |
| 운영 커리큘럼 | `curriculum` — 초기 과제 4개 |

- 재고표, 미결 금액, 오른편 이력은 모두 같은 테이블을 조회해 계산합니다. 표시용 값은 따로 저장하지 않습니다.
- 사용자 응답·수정은 `confirmed_case`에 확정 사례로만 쌓입니다. 규칙으로 자동 승격하지 않습니다.
- 시험 데이터: 기준정보 행은 `is_test=1`이고, 기본적으로 `data/etm_demo.db`에만 들어갑니다. 운영 DB(`data/etm.db`)와 파일이 분리됩니다.

## 4. KPP·운반비 처리
- 팔레트는 `item.kind='rental'`(소유자 KPP)로 두고, 공장에서 현장으로 옮긴 위치 이동만 기록합니다. 회사 재고와 섞이지 않습니다.
- KPP 임대료 채무는 자동으로 만들지 않습니다(KPP-NO-AUTO).
- 운반비 채무는 운송업체(상대방)가 확정됐을 때만 만듭니다. 금액이 없으면 미확정 채무입니다.

## 5. 화면
- 왼쪽: 새 자료 입력, 또는 현재 사건 하나(남은 일 칩 → 확인할 것 → 접힌 '내용·수정' → 접힌 '원본·처리 이력').
- 오른쪽: 처리일별 이력. 한 줄 요약에, 사건별 최신 줄에만 남은 일을 붙입니다.
- 상단 한 줄: 재고·받을 돈·줄 돈·현장 팔레트. 상세는 누를 때 펼칩니다.
