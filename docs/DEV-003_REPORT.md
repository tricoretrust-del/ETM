## 1. 세 축의 책임 (구현 기준)

| 축 | 보관하는 것 | DB |
|---|---|---|
| 운영 RBK | 어떤 조건에서 어떤 처리를 재사용할지: 승인된 규칙 버전·범위·근거·적용 이력 | `rule`, `rule_version`, `judgment`(승인), `rule_application` |
| 운영 LAG | 무엇을 아직 모르는지: 질문·근거·검증·판정 | `lag`, `lag_link`, `lag_log`, `verification`, `verification_case`, `judgment` |
| **운영 PLN** | 무엇을 실행하고 무엇으로 완료를 판단할지: 조치·완료 조건·담당·기한·진행·결과 | **`plan`, `plan_link`, `plan_log`** (신규) |

세 축의 상태는 서로 독립입니다. **PLN 완료는 LAG 판정이나 RBK 승인을 일으키지 않습니다.** PLN 상태가 바뀌어도 재고·채권·채무는 변하지 않습니다.

## 2. 실제 DB 구조 (마이그레이션 0004, 비파괴)

```
plan ─┬─ plan_link (role: basis 근거 | target 대상 | evidence 완료 증빙)
      │      └─ 대상은 정확히 하나: lag | event | intake(증빙) | rule_version | decision_case | obligation
      └─ plan_log (버전·동작·이전→새 상태·바뀐 값·사유·주체·시각)
reclassification (source_table, source_id UNIQUE → target_layer, target_ref, status, reason)
lag.layer ('ops' | 'trnk')
```

- `plan`: 안정 ID(화면 표기 PLN-n), 회사, 제목, 목적·조치·완료 조건(미확정 허용), 상태, 사유, 담당·기한, 실행 지시자·시각, 결과, 완료 시각, 출처, 생성자·시각, **수정 버전(version)**·수정 시각
- DB 제약:
  - 상태 값 CHECK
  - DRAFT·CANCELLED가 아니면 실행 지시자 필수(CHECK)
  - DONE이면 결과·완료 시각·완료 조건 필수(CHECK)
  - DONE으로 바꿀 때 해제되지 않은 증빙 연결 필수(트리거)
  - 완료된 계획의 조건·조치·목적은 수정 불가(트리거)
  - 연결은 삭제 불가, 해제할 때는 사유를 남김(트리거·CHECK)
  - 사건·LAG·증빙·규칙 버전·확인 기록·미결 의무에 대해 회사 경계 검사(트리거 6개)
- 기존 거래·규칙·LAG 데이터는 그대로 둡니다. 0003까지 적용된 DB에 0004를 적용해도 기존 행 수가 변하지 않는 것을 테스트로 확인했습니다.

## 3. 상태 전이·권한

```
DRAFT ─실행 지시─▶ READY ─시작─▶ IN_PROGRESS ─완료(결과+증빙)─▶ DONE ─재개(사유)─▶ IN_PROGRESS
  │                 │ ▲                │                                    (이전 결과는 이력에 보존)
  └▶ CANCELLED      ▼ │ 재개(사유)      ▼
                BLOCKED / DEFERRED (사유 필수) ──▶ CANCELLED
```

| 동작 | 권한 |
|---|---|
| 계획 생성·수정·연결·시작·완료 등록 | 사람 사용자(operator·approver). system 불가 |
| **실행 지시(DRAFT → READY)**, 차단·보류 상태에서 재개, 완료 후 재개 | 승인권자(approver/admin) 또는 **지정된 담당자** |
| 직접 실행을 지시한 사용자 | 생성과 READY 전환을 한 동작으로 처리(`execute_now`) |

- 승인된 범위(목적·조치·완료 조건)를 바꾸면 **DRAFT로 돌아가 다시 실행 지시**가 필요합니다. 담당·기한 변경은 승인을 유지합니다.
- 모든 변경은 `expected_version` 검사(동시 수정 충돌 시 거부), 트랜잭션, `request_id` 멱등성을 거칩니다.

## 4. 메커니즘·화면

- 흐름: 사건 → (+ LAG 질문) → LAG에 **실행계획 여러 개** 연결 → 실행 지시 → 진행 → 결과·증빙으로 완료 → LAG에서 별도로 검증·판정 → 필요하면 RBK 버전
- 계획은 LAG 없이도 만들 수 있습니다(사건 상세의 "+ 실행계획", 패널의 "직접 만들기"). 사용자 수정이나 오타를 계기로 계획을 자동 생성하지 않습니다.
- 완료 등록 때 이미 연결된 사건·증빙을 완료 근거로 재사용합니다. 결과 문장을 LAG에 다시 입력할 필요가 없습니다.
- 화면:
  - 상단 **RBK·PLN·LAG** 패널에 PLN 섹션, LAG 카드의 연결 계획, 재분류 기록이 있습니다.
  - PLN 상세: 필드, 연결(해제 이력 포함), 변경·실행 이력, 상태별로 필요한 버튼만 표시
  - 사건 상세: 관련 계획과 "+ 실행계획 / + LAG(질문)"
- TRNK Docs와 자동 동기화하지 않습니다. 운영 계획 상태의 정본은 DB이고, 출처는 `origin`과 재분류 기록의 `target_ref`로 남깁니다.

## 7. 미해결 판단 (TRNK)

1. **실행 지시 권한**: "승인권자 또는 지정 담당자"로 구현했습니다. 담당자 본인의 자기 지시를 허용할지 확인이 필요합니다.
2. **LAG#1(미결·완결 세부 상태)**: Docs에 대응하는 LAG ID가 없어 'TRNK 등록 대기'입니다. TRNK LAG에 등록하면 ID를 알려 주십시오.
3. **PLN 기한 경과 알림, 우선순위 필드**는 지시서 범위 밖이라 만들지 않았습니다.
4. **PLN → TRNK PLN·DEV 연결**: 현재는 `origin`·`reclassification.target_ref`에 문서 ID를 글자로 적습니다. Docs 항목 ID 체계가 정해지면 검증 가능한 참조로 바꿀 수 있습니다.
5. **인증**은 여전히 화면의 사용자 선택뿐입니다(DEV-002 보고서 §7).
